# FactoryGuard AI

**Predictive maintenance & quality inspection platform for manufacturing units**
Team 17 · Neural Stack Knights · Problem NSK-17 · Domain: Manufacturing & Quality Control

A pharmaceutical packaging unit near Visakhapatnam runs 40 machines in three shifts. Breakdowns are unexpected,
defects surface only at final inspection, maintenance logs sit in unread registers and nobody can say which
machine costs the most downtime. FactoryGuard AI replaces the paper with a full-stack web app — machines,
production, sensors, maintenance, spares, quality and downtime in one database — and puts AI and GenAI directly
into the shop-floor workflow.

## Quick start (2 minutes)

Requirements: **Python 3.10+** (no Node build, no external services, no API key needed).

```bash
python run.py          # Windows: double-click run.bat  ·  macOS/Linux: ./run.sh
```

That single file does everything: creates `backend/.venv`, installs the packages, copies `.env.example` to `.env`,
trains/loads the ML models, seeds 30 days of synthetic plant data, starts the server and opens
**http://localhost:8000** in your browser (Swagger API docs at **/docs**). Press Ctrl+C to stop.

| Option | What it does |
|---|---|
| `python run.py --port 9000` | use another port |
| `python run.py --reset` | wipe the demo database and re-seed |
| `python run.py --host 0.0.0.0` | let other devices on your network open it |
| `python run.py --test` | start, run the 82 end-to-end API checks, stop |
| `python run.py --no-browser` | don't open a browser tab |

Manual alternative: `cd backend && pip install -r requirements.txt && uvicorn app.main:app --port 8000`.

| Role | Username | Password | Lands on |
|---|---|---|---|
| Admin | `admin` | `Admin@123` | Plant dashboard + administration |
| Plant head | `planthead` | `Plant@123` | Plant dashboard, AI insights, shift reports |
| Maintenance technician | `tech1` … `tech5` | `Tech@123` | My work: assigned tickets, at-risk machines |
| Machine operator | `op01` … `op15` | `Oper@123` | My shift: log production / readings / issues |

### Optional: live LLM

Copy `.env.example` to `.env` and set **one** of `GEMINI_API_KEY`, `GROQ_API_KEY` or `OPENAI_API_KEY`.
Without a key every GenAI feature still works through a deterministic offline engine (retrieval + templates);
the UI shows which provider answered (`Offline engine` vs `LLM · gemini`). If the LLM call fails, the app falls back
automatically.

### Optional: PostgreSQL / MySQL

Set `DATABASE_URL` in `.env` (`pip install psycopg2-binary` or `pymysql`), or run `docker compose up --build`
for app + PostgreSQL. DDL scripts for all three databases are in `database/`.

## What's inside

### Modules (all requirements)

| Requirement | Where |
|---|---|
| Secure login, role-based access for 4 roles | JWT + PBKDF2 (200k iterations), `require_roles()` on every endpoint, role-specific navigation |
| Machine registry with specs & maintenance history | *Machines* page → machine panel (specs, limits, PM schedule, ticket + downtime history, MTTR) |
| Shift-wise production & sensor logs | *Production* (per-batch OEE), *Sensor readings* (manual, IoT history, simulator) |
| Maintenance ticket workflow | open → assigned → in progress ⇄ on hold → resolved → verified & closed; state machine enforced server-side; root cause & action required to resolve; activity timeline; parts issued |
| Quality inspection per batch | *Quality* — sample, defects, defect type, process parameters, AQL-style auto result |
| Shift & operator management | *Shifts & roster* — 3 shifts, supervisors, daily operator/technician → shift → machine assignment |
| Spare parts inventory | *Spare parts* — stock, reorder levels, goods receipt / write-off, parts consumed per ticket with cost |
| Downtime records with reasons | *Downtime* — 8 reason categories, planned/unplanned, ongoing stops, linked tickets |
| Admin dashboard | OEE + A/P/Q, OEE trend, shift comparison, downtime Pareto, downtime by machine, defects by type, lowest-OEE machines, MTBF/MTTR, open tickets by priority, low stock, alerts |
| Synthetic / public data only | All data generated by `app/seed.py`; ML trained on AI4I-2020-style synthetic data |

### AI features (scikit-learn) — built into the workflow

| Feature | Model | Where it acts | Hold-out metrics |
|---|---|---|---|
| **Failure prediction** — P(failure in next 24 h), failure mode, top drivers, est. hours to failure | RandomForest (200 trees) + mode classifier | Re-scored on incoming readings; machine panel, live floor tiles, fleet ranking; raises alerts and **auto-creates predictive tickets** above the threshold | ROC-AUC 0.96, F1 0.94, precision 0.96, recall 0.92 |
| **Anomaly detection** on every sensor reading | IsolationForest + per-sensor z-score + machine limits (ISO 10816 vibration zones) | Flags readings, explains *why*, raises alerts; persistent critical anomalies auto-open a ticket (debounced: 2 of last 3 readings) | 70% detection on failure states, 1.7% false alarms |
| **Batch defect risk** — pre-batch check | GradientBoosting + defect-type classifier | *Quality → Pre-batch risk check*; risk stored on every inspection; recommends hold / tightened sampling and lists out-of-spec parameters with corrective actions | ROC-AUC 0.92, accuracy 0.86 |

Training data follows the physics-style failure rules of the public **AI4I 2020 Predictive Maintenance dataset**
(UCI / Kaggle: tool-wear, heat-dissipation, power, overstrain) extended with bearing (vibration) and pneumatic
(pressure) failure modes for packaging machines. Retrain any time: `python -m app.ml.train` or *Settings → Retrain*.
Metrics: `backend/app/ml/artifacts/metrics.json`; sample training rows are saved next to it.

### GenAI features (Gemini / Groq / OpenAI)

| Feature | User | How it works |
|---|---|---|
| **Troubleshooting copilot** | Technician | RAG: TF-IDF retrieval over 7 maintenance manuals, restricted to the machine's own manual + general SOP, combined with the machine's live readings, anomaly flags and past root causes. Cites manual sections. Multi-turn. |
| **Shift performance report** | Plant head | All numbers (OEE, downtime Pareto, defects, tickets, risk, low stock, per-operator output) are computed in SQL/Python first; the LLM only writes the narrative and next-shift actions — prompt forbids inventing data. Printable. |
| **Smart ticket triage** | Operator | Operator's free text + live sensor context + spare-parts list → JSON (category, priority, probable causes, first checks, suggested part numbers, safety note). Output is validated: part numbers must exist, AI may raise but never lower priority. |
| **Quality RCA & CAPA** | Plant head / QA | Failed batch + process parameters + ML defect assessment + machine sensor summary → ranked root causes, containment, CAPA with owners. |

Prompts live in `backend/app/genai/assistants.py`. Every call is logged in `genai_logs` (feature, provider, latency).

### Bonus features

* **Real-time sensor simulation** — background thread streams readings for every running machine; hidden degradation
  (bearing wear, heater overheating, air leak, tool overstrain) grows over time so the models have something to catch.
  Resolving the machine's ticket "repairs" it. *AI insights → Inject fault* lets you trigger a failure during the demo.
* **Spare-parts reorder alerts** — stock at/below reorder level raises an alert (critical at zero), reorder report
  with suggested order quantity, cost, supplier and lead time; receipt clears the alert.
* **OEE** — Availability × Performance × Quality per batch, machine, shift, line, machine type, operator and day
  (`/api/analytics/oee`).

### Security & validation

JWT bearer tokens (8 h), PBKDF2-SHA256 password hashing, password strength rule, account lockout after 5 failed
logins, login rate limiting, role checks on every endpoint (operators edit only their own logs for 24 h; only plant
head/admin verify & close tickets; technicians only self-assign), Pydantic range and cross-field validation
(rejected ≤ produced, run ≤ planned time, end > start, no future dates, defects ≤ sample), DB check constraints and
unique keys, ticket state machine, no deletion of machines with production history (GMP data integrity), full audit
log, security headers, parameterised ORM queries, XSS-safe rendering in the UI.

(per shift/batch with OEE inputs), `sensor_readings` (with anomaly result), `maintenance_tickets`,
`ticket_activities`, `spare_parts`, `part_usages`, `quality_inspections` (process params + AI risk),
`downtime_events`, `alerts`, `failure_predictions`, `settings`, `audit_logs`, `genai_logs`.

## Suggested 5-minute demo

1. **Plant head** → dashboard: OEE 81% vs 75% target, downtime Pareto shows breakdowns as the top loss, BP-03 at 90% risk.
2. **AI insights** → inject *bearing wear* on a machine → **Live floor** turns its tile amber/red within a minute; open
   it to see failure probability, failure mode and drivers; a predictive ticket and alert appear automatically.
3. **Operator** (`op01`) → *Report issue* → "grinding noise…" → AI triage suggests category, priority, causes, bearing part.
4. **Technician** (`tech1`) → *Assign to me* → *Start work* → *Ask copilot* (manual steps with citations) → issue bearing →
   resolve with root cause → simulator stops degrading the machine.
5. **Plant head** → verify & close → *Shift reports* → generate the AI shift report → *Quality* → RCA on a failed batch →
   *Pre-batch risk check* with sealing temp 166 °C → "HOLD batch".
6. *Spare parts* → reorder report.

All data is synthetic. No real factory data is used.
